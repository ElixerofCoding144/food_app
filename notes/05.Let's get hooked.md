# Let's Get Hooked

Everything React does can ultimately be built using **JavaScript, HTML, and CSS**. React itself is written in JavaScript and runs in the browser through JavaScript.

So why use React?

## Why React Is Useful

React gives us a structured way to build interactive user interfaces.

* **Reusable components:** Build the interface from small components and reuse them throughout the application.
* **Declarative UI:** Describe what the interface should look like for a particular state. React handles updating the DOM.
* **State-driven updates:** Keep application data and the UI synchronized without manually querying and modifying DOM elements.
* **Less duplicated code:** Shared components and reusable patterns reduce repetition.
* **Developer experience:** React provides clear conventions, useful tooling, and a large ecosystem.
* **Scalable structure:** Components help organize increasingly complex applications.

> **Important:** React does not automatically make an application fast or optimized. Performance still depends on architecture, component design, data handling, and rendering strategy.

---

## Library or Framework?

React is primarily a **UI library**, not a complete application framework.

React mainly handles:

* Components
* Rendering
* State
* User-interface updates

Other tools are commonly added for concerns such as:

* Routing
* Data fetching
* Styling
* Testing
* Build tooling
* Application architecture

### The Main Idea

React does not replace JavaScript.

Instead, React gives JavaScript a **component-based, declarative, and state-driven model** for building interactive user interfaces.

# Part 1 — Organizing a React Application

## Architectural Refinements

At this stage, the application introduces two important architectural improvements:

1. **File reorganization**
2. **ES modules using `import` and `export`**

In the earlier implementation documented in [05.creating-a-food-delivery-app](https://github.com/ElixerofCoding144/food_app/tree/main/05.creating-a-food-delivery-app), every component lived inside `App.js`.

That works for a small prototype, but it becomes difficult to maintain as the application and component hierarchy grow.

Instead, components should be extracted into meaningfully named modules.

This improves:

* **Separation of concerns**
* **Readability**
* **Maintainability**
* **Reusability**
* **Scalability**

The `import` and `export` syntax allows these modules to communicate without putting the entire application inside one file.

### Basic Workflow

**Step 1:** Create separate JavaScript files for components.

For example:

```text
Header.js
Body.js
RestaurantCard.js
```

**Step 2:** Export the component from its file.

You can use either:

* Default exports
* Named exports

**Step 3:** Import the component wherever it is required.

The import syntax must correspond to the type of export being used.

### Reference

[Importing and Exporting Components](https://react.dev/learn/importing-and-exporting-components)

## `RestaurantCard.js`

`RestaurantCard.js` represents a single restaurant.

Instead of owning restaurant data itself, the component receives data through a prop called `resData`.

```jsx
const RestaurantCard = ({ resData }) => {
  return (
```

### Key Concept: Props

`RestaurantCard` does not need to know where the restaurant data came from.

It simply receives:

```jsx

```

and uses that data to render its UI.

This makes the component reusable.

## `Body.js`

`Body.js` imports `RestaurantCard` and renders a card for every restaurant.

```jsx
import RestaurantCard from "./RestaurantCard";

const Body = () => {
  return (

      <div className="res-container">

          <RestaurantCard

            resData={restaurant.info}
          />
        ))}
      </div>

```

The important expression is:

```jsx
resObj.map((restaurant) => (
  <RestaurantCard
    key={restaurant.info.id}
    resData={restaurant.info}
  />

```

### What Is Happening Here?

For every restaurant inside `resObj`:

```text
restaurant object
      ↓
restaurant.info
      ↓
resData prop
      ↓
RestaurantCard
      ↓
Rendered restaurant UI
```

React therefore turns an array of restaurant data into an array of components.

# Part 5 — Separate Data from Components

At this point, restaurant data may still be declared directly inside `Body.js`.

For example:

```js
const restaurants = [
  {
    id: "pizza-hut",
    name: "Pizza Hut",
    imageUrl: "https://example.com/pizza.jpg",
    rating: 4.2,
    cuisine: "Pizzas",
    deliveryTime: 42,

```

This works, but it mixes two responsibilities:

```text
Body.js
├── UI logic
└── Application data
```

A better structure separates them.

> **Rule of thumb:** Avoid keeping large hardcoded datasets inside component files.

Move mock restaurant data into something like:


```text

```

The project can then evolve toward:

```text
src/
├── components/
│   ├── Body.js
│   ├── Header.js
│   └── RestaurantCard.js
│
└── utils/
    ├── constants.js
    └── mockData.js
```

This creates clearer responsibilities:

| File                | Responsibility                  |
| ------------------- | ------------------------------- |
| `Body.js`           | Restaurant-list UI and behavior |
| `RestaurantCard.js` | Presentation of one restaurant  |
| `Header.js`         | Header UI                       |
| `mockData.js`       | Mock restaurant data            |
| `constants.js`      | Shared constant values          |

# Part 6 — Default Exports vs Named Exports

JavaScript modules provide two common export styles.

## Default Export

A module can have one default export.

```jsx
const Header = () => {
  return <header>...</header>;
};

export default Header;
```

Import it without curly braces:

```jsx
import Header from "./components/Header";
```

---

## Named Export

A module can expose multiple named exports.

```js
export const CDN_URL = "...";
export const LOGO_URL = "...";
```

Import them using curly braces:

```js
import { CDN_URL, LOGO_URL } from "../utils/constants";
```

### Quick Comparison

| Type    | Export                          | Import                                          |
| ------- | ------------------------------- | ----------------------------------------------- |
| Default | `export default Header;`        | `import Header from "./Header";`                |
| Named   | `export const CDN_URL = "...";` | `import { CDN_URL } from "../utils/constants";` |

> **Remember:** The import syntax must match the export syntax.

---

## When Should I Use Each?

### Default Export

Use a default export when a module has one obvious primary value.

For example:

```text
Header.js
RestaurantCard.js
Body.js
```

```jsx
export default Header;
```

### Named Exports

Named exports are useful when a module exposes several related values.

For example:

```js
export const CDN_URL = "...";
export const LOGO_URL = "...";
```

---

## Can Default and Named Exports Be Imported Together?

Yes.

If `Header.js` exposes both:

```jsx
export default Header;
export { Logo };
```

they can be imported together:

```jsx
import Header, { Logo } from "./Header";
```

Here:

```text
Header → default import
Logo   → named import
```

---

## Does Importing a Component Render It?

**No.**

This:

```jsx
import Header from "./Header";
```

only makes `Header` available inside the current module.

The component renders only when it becomes part of the rendered JSX:

```jsx
return (
  <div>
    <Header />
  </div>
);
```

Think of it as:

```text
Import
  ↓
Component becomes available
  ↓
Use component in JSX
  ↓
React renders component
```

# Part 8 — The Problem: Data and UI Out of Sync

Consider:

```jsx
const Body = () => {
  let resObj = [
    {
      info: {
        id: "pizza-hut",
        name: "Pizza Hut",
        avgRating: 4.2,
      },
    },
    {
      info: {
        id: "burger-king",
        name: "Burger King",
        avgRating: 3.8,
      },
    },
  ];

  return (
    <div>
      <button
        onClick={() => {
          resObj = resObj.filter(
            (restaurant) => restaurant.info.avgRating > 4
          );

          console.log(resObj);
        }}
      >
        Top Rated Restaurants
      </button>

      <div className="res-container">
        {resObj.map((restaurant) => (
          <RestaurantCard
            key={restaurant.info.id}
            resData={restaurant.info}
          />
        ))}
      </div>
    </div>
  );
};
```

When the button is clicked, this executes:

```js
resObj = resObj.filter(
  (restaurant) => restaurant.info.avgRating > 4
);
```

The JavaScript variable changes.

The console confirms it:

```text
[
  {
    info: {
      name: "Pizza Hut",
      avgRating: 4.2
    }
  }
]
```

But there is a problem.

## The Issue

1. The array changes.
2. `console.log()` shows the new array.
3. The browser UI still shows the old restaurant list.

In other words:

```text
JavaScript data → changed ✓
React UI       → unchanged ✗
```

Why?

---

# Part 9 — React Does Not Track Ordinary Variables

Consider:

```js
let count = 0;

count = count + 1;
```

JavaScript knows that `count` changed.

React does **not** automatically treat that assignment as a reason to render the component again.

The same applies here:

```js
resObj = filteredRestaurants;
```

Changing an ordinary variable does not tell React:

> "The information used by this component has changed. Render the component again."

This is where **state** becomes necessary.

---

# Part 10 — What Causes a React Component to Render Again?

For our current mental model, a component can render again when React processes an update such as a **state update**, or when its parent renders it again with new inputs.

The key mechanism we need for our filtering example is:

```text
State changes
    ↓
React schedules an update
    ↓
Component renders again
    ↓
JSX is calculated using the new state
    ↓
React updates the necessary DOM
```

This is fundamentally different from changing a normal variable.

---

# Part 11 — What Is State?

State is information that a component needs to **remember between renders** and that can affect what the component displays.

Examples include:

```text
Restaurant list
Search text
Selected restaurant
Shopping-cart contents
Logged-in status
Counter value
Expanded/collapsed state
Selected filter
```

A useful mental model is:

> **State is a component's memory.**

React provides Hooks that allow function components to use React features such as state.

The Hook we need first is:

```jsx
useState
```

---

# Part 12 — Introducing `useState`

Import it from React:

```jsx
import { useState } from "react";
```

Then create state:

```jsx
const [listOfRestaurants, setListOfRestaurants] = useState(resObj);
```

At first this syntax can look unusual.

Break it into three pieces:

```text
listOfRestaurants
        ↓
current state value

setListOfRestaurants
        ↓
function used to request a state update

useState(resObj)
        ↓
initial state
```

So:

```jsx
const [listOfRestaurants, setListOfRestaurants] = useState(resObj);
```

means:

> Start with `resObj` as the restaurant list, and give me a state value plus a function for updating that state.

---

# Part 13 — Why Hooks Feel Like "Super-Powered Variables"

A normal variable can hold data:

```js
let restaurants = resObj;
```

But changing it:

```js
restaurants = filteredRestaurants;
```

doesn't by itself ask React to render the component again.

State gives React a way to remember the value and associate updates to it with the component's rendering process.

```jsx
const [restaurants, setRestaurants] = useState(resObj);
```

Then:

```jsx
setRestaurants(filteredRestaurants);
```

requests a state update.

A better definition than "super-powered variables" is:

> **State values are React-managed values that persist between renders and whose updates can trigger rendering.** In other words, whenever a state variable updates, react will re-render the component.

---

# Part 14 — Fixing the Restaurant Filter with State

We can now rewrite the filtering example:

```jsx
import { useState } from "react";
import RestaurantCard from "./RestaurantCard";
import resObj from "../utils/mockData";

const Body = () => {
  const [listOfRestaurants, setListOfRestaurants] = useState(resObj);

  return (
    <div className="body">
      <button
        onClick={() => {
          const filteredRestaurants = listOfRestaurants.filter(
            (restaurant) => restaurant.info.avgRating > 4
          );

          setListOfRestaurants(filteredRestaurants);
        }}
      >
        Top Rated Restaurants
      </button>

      <div className="res-container">
        {listOfRestaurants.map((restaurant) => (
          <RestaurantCard
            key={restaurant.info.id}
            resData={restaurant.info}
          />
        ))}
      </div>
    </div>
  );
};

export default Body;
```

Now the flow becomes:

```text
Initial restaurant data
        ↓
useState(resObj)
        ↓
listOfRestaurants
        ↓
UI renders restaurant cards
        ↓
User clicks "Top Rated Restaurants"
        ↓
filter()
        ↓
setListOfRestaurants(filteredRestaurants)
        ↓
State update
        ↓
React renders Body again
        ↓
UI reflects the filtered state
```

That relationship is one of the most important ideas in React.

# Part 15 — Normal Variable vs State

| Normal JavaScript Variable              | React State                                |
| --------------------------------------- | ------------------------------------------ |
| Stores a value                          | Stores a value associated with a component |
| Can change                              | Can change through its setter              |
| Does not itself trigger React rendering | Updating it can trigger rendering          |
| Recreated during a component render     | React preserves state between renders      |
| React does not track assignments to it  | React manages state updates                |

The important distinction is therefore not simply:

```text
variable vs special variable
```

It is:

```text
ordinary JavaScript value
        vs
value participating in React's rendering model
```

# Part 16 — The Core React Mental Model

React becomes much easier to understand when you stop thinking primarily in terms of manually changing HTML.

Instead, think:

```text
STATE
  ↓
COMPONENT
  ↓
JSX
  ↓
UI
```

When state changes:

```text
NEW STATE
    ↓
COMPONENT RENDERS AGAIN
    ↓
NEW JSX
    ↓
REACT RECONCILES THE RESULT
    ↓
DOM UPDATED WHERE NECESSARY
```

You describe what the UI should look like for the current state.

React handles synchronizing that description with the DOM.

That is the foundation of **declarative UI**.

# Part 17 — Key Takeaways

By this point, you should understand the following ideas.

### Architecture

* Components should be separated into meaningful modules.
* `import` and `export` connect those modules.
* Component files should focus primarily on component responsibilities.
* Large hardcoded datasets can be extracted into dedicated modules.
* Shared constants can live in files such as `constants.js`.

### Components

* Components can receive information through props.
* `.map()` can transform data collections into collections of components.
* Elements rendered from collections need stable keys.

### Modules

* Default exports are useful when a module has one primary export.
* Named exports are useful when a module exposes multiple related values.
* Import syntax must correspond to export syntax.
* Importing a component does not automatically render it.

### State

* Ordinary JavaScript variables can change without causing React to update the UI.
* Components sometimes need information that persists between renders.
* React calls this information **state**.
* `useState` lets a function component declare state.
* The state setter requests an update.
* React can then render the component using the new state.

# Quick Revision

### What is React?

A JavaScript library for building user interfaces using components and declarative rendering.

### Why separate components into files?

To improve organization, separation of concerns, maintainability, and scalability.

### What is a prop?

Information passed from one component to another.

### What does `map()` do in our restaurant application?

It transforms restaurant data into `RestaurantCard` elements.

### Why doesn't changing `resObj` update the UI?

Because assigning a new value to an ordinary JavaScript variable does not notify React that the component needs to render again.

### What is state?

Information React preserves for a component between renders and that can affect its UI.

### What does `useState` return?

Two values:

```jsx
const [state, setState] = useState(initialValue);
```

Conceptually:

```text
state
  → current value

setState
  → function for requesting an update
```

### What happens when state is updated?

```text
State update
    ↓
React schedules rendering
    ↓
Component executes again
    ↓
New JSX is produced
    ↓
React updates the necessary DOM
```

---

> **In React, instead of manually changing the UI whenever data changes, we update state and let React render the UI that corresponds to that state.**

### Note:
The following statement uses **array destructuring** to assign the two values returned by `useState`:

```jsx
const [resObj, setResObj] = useState(resList);
```

It is equivalent to first storing the returned array and then destructuring it:

```jsx
const stateValues = useState(resList);
const [resObj, setResObj] = stateValues;
```

Without array destructuring, the same values can be accessed by their indexes:

```jsx
const stateValues = useState(resList);
const resObj = stateValues[0];
const setResObj = stateValues[1];
```

The first element, at index `0`, is the current state value. The second element, at index `1`, is the state setter function.
